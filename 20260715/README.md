# 2026-07-15 학습 정리 - React key와 리스트 항목의 정체성

## 오늘의 개념

React의 `key`는 리스트를 렌더링할 때 이전 렌더의 항목과 다음 렌더의 항목을 같은 항목으로 매칭하기 위한 식별자다.

단순히 warning을 없애기 위한 값이 아니라, 컴포넌트 state, input 값, focus 같은 UI 상태가 어느 항목에 붙어 있어야 하는지 React에게 알려주는 장치다.

## key가 필요한 이유

React는 상태가 바뀔 때마다 JSX 결과를 다시 만들고, 이전 렌더 트리와 다음 렌더 트리를 비교한다.

리스트에서는 같은 컴포넌트가 여러 개 반복되기 때문에, React가 "이전의 어떤 항목이 다음의 어떤 항목으로 이어지는지" 알아야 한다.

이때 `key`가 안정적이면 React는 항목의 정체성을 유지하면서 필요한 부분만 갱신할 수 있다.

반대로 `key`가 불안정하면 React는 서로 다른 항목을 같은 항목으로 착각하거나, 같은 항목을 새 항목으로 취급할 수 있다.

그 결과 DOM 재사용뿐 아니라 각 항목 안의 state, input 값, focus, 애니메이션 상태가 잘못된 데이터에 붙을 수 있다.

## index key가 위험한 이유

배열 index는 항목 자체의 정체성이 아니라 "현재 위치"를 뜻한다.

리스트의 맨 앞에 새 항목이 추가되면 기존 항목들의 index가 모두 밀린다.

React 입장에서는 `key={0}`이던 첫 번째 컴포넌트가 여전히 같은 항목이라고 판단하지만, 실제 데이터는 다른 항목으로 바뀐다.

이 차이 때문에 uncontrolled input 값이나 항목 내부 state가 엉뚱한 데이터에 남아 있는 버그가 생긴다.

## index를 key로 써도 되는 경우

다음 조건을 모두 만족하면 index key를 쓸 수 있다.

- 리스트가 정적이다.
- 추가, 삭제, 정렬, 필터링이 없다.
- 각 항목 내부에 독립적인 state나 input 상태가 없다.
- 데이터에 사용할 수 있는 안정적인 id가 정말 없다.

하지만 실무에서는 처음엔 정적 리스트처럼 보여도 나중에 정렬, 필터, 삽입 요구사항이 들어오는 일이 많다.

그래서 가능하면 `id`, `slug`, 서버 primary key처럼 데이터의 생명주기와 함께 가는 값을 `key`로 사용한다.

## 코드 예시

`index.tsx`는 같은 리스트를 두 방식으로 렌더링한다.

- 왼쪽: `key={member.id}`를 사용한다.
- 오른쪽: `key={index}`를 사용한다.

각 input에 값을 입력한 뒤 "맨 앞에 추가" 버튼을 누르면, index key 쪽은 입력 상태가 기대와 다르게 다른 항목에 붙을 수 있다.

## 실무 관점

시니어는 `key`를 "렌더링 warning 제거용 속성"이 아니라 "UI 항목의 identity 설계"로 본다.

리스트에 입력, 체크박스, 드래그 앤 드롭, 애니메이션, 낙관적 업데이트가 들어가면 key 안정성은 버그 재현성과 직결된다.

코드 리뷰에서는 `key={index}`가 보이면 먼저 리스트가 정말 정적인지, 앞으로 정렬/필터/삽입 가능성이 없는지 확인해야 한다.

## 오늘의 핵심 문장

`key`는 React에게 "이 항목은 위치가 아니라 이 데이터다"라고 알려주는 식별자다.
