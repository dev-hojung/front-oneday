# React 렌더링 비용과 브라우저 렌더링 비용

## 핵심 구분

React 렌더링 비용을 줄이는 도구는 **컴포넌트 트리 안에서 불필요한 재계산과 재렌더를 줄이는 도구**다.

브라우저 렌더링 비용을 줄이는 도구는 **DOM이 실제 픽셀로 바뀌는 과정, 즉 레이아웃·페인트·컴포지팅 비용을 줄이는 도구**다.

이 둘을 섞어서 보면 최적화 방향이 자주 빗나간다. React Profiler에서 느린 컴포넌트를 봐야 할 때 CSS만 만지거나, 반대로 레이아웃 thrashing이 문제인데 `React.memo`만 붙이는 식의 실수가 생긴다.

## React 렌더링 비용을 줄이는 도구

- `React.memo`: props가 바뀌지 않은 컴포넌트의 재렌더를 건너뛴다.
- `useMemo`: 비싼 계산 결과를 의존성 기준으로 캐싱한다.
- `useCallback`: 함수 참조를 안정화해 memoized child의 불필요한 렌더를 줄인다.
- `useDeferredValue`, `startTransition`: 급하지 않은 UI 업데이트의 우선순위를 낮춘다.
- 리스트 가상화: `react-window`, `react-virtualized`처럼 화면에 보이는 행만 렌더링한다.
- React DevTools Profiler: 어떤 컴포넌트가 왜, 얼마나 오래 렌더링됐는지 측정한다.

## 브라우저 렌더링 비용을 줄이는 도구

- `content-visibility: auto`: 화면 밖 콘텐츠의 렌더링 작업을 필요할 때까지 미룬다.
- `contain`: 요소 내부 변화가 바깥 레이아웃과 페인트에 미치는 영향을 제한한다.
- `contain-intrinsic-size`: 아직 렌더링하지 않은 콘텐츠의 예상 크기를 예약한다.
- `transform`, `opacity`: 레이아웃 재계산 없이 컴포지팅 중심으로 처리하기 쉬운 애니메이션 속성이다.
- `will-change`: 곧 바뀔 속성을 브라우저에 힌트로 알려 최적화 준비를 돕는다.
- Chrome DevTools Performance: 레이아웃, 페인트, 스크립트 비용이 어디서 발생하는지 추적한다.

## 화면 밖 콘텐츠의 실제 크기를 모를 때 생기는 문제

`content-visibility: auto`를 쓰면 브라우저는 화면 밖 콘텐츠의 렌더링을 미룰 수 있다. 그런데 아직 실제 높이를 계산하지 않았다면, 브라우저는 문서 전체의 스크롤 길이를 정확히 모른다.

그 결과 사용자가 스크롤해서 해당 콘텐츠가 가까워지는 순간 실제 크기가 확정되고, 스크롤바 위치나 레이아웃이 갑자기 흔들릴 수 있다.

그래서 보통 다음처럼 예상 크기를 같이 준다.

```css
.article-card-list {
  content-visibility: auto;
  contain-intrinsic-size: 320px;
}
```

의미는 단순하다.

> 아직 실제로 렌더링하지 않았더라도, 이 요소는 대략 320px 높이라고 가정하고 공간을 잡아둬.

## 실무 판단

React 최적화는 **컴포넌트 렌더링이 많이 발생하는가**를 먼저 본다. 브라우저 최적화는 **레이아웃, 페인트, 컴포지팅 비용이 큰가**를 먼저 본다.

시니어 성장 관점에서는 “무슨 최적화 기법을 아는가”보다 “지금 느린 원인이 어느 계층에 있는지 구분할 수 있는가”가 더 중요하다.
